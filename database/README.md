# HiCo Thermal Knowledge Database

`database/` is the generated, validated knowledge layer for HiCo Thermal. It is built from the canonical
`thermal-data/` source dataset and the `generated-thermal/` candidate dataset, while preserving the existing
Xiaomi runtime compatibility table under `devices/`.

## Data layers

- `devices/` — normalized runtime profiles generated from the existing Xiaomi device records.
- `thermal-data/` — original thermal-relevant source files and repository manifests; this is the canonical raw dataset.
- `generated-thermal/` — HiCo candidates generated from the raw source files and verified by `hicod thermal check`.
- `database/thermal/` — normalized source/provenance index generated by `hico_database.py build`.
- `database/mapped/` — deterministic artifact mappings produced by the thermal mapping tools.
- `database/tables/` — static thermal value tables.
- `database/schema/` — machine-readable schemas used by validation.

## Identity model

A thermal source records the provider, repository, branch and exact source commit separately from the detected
OEM, ROM family, device, Android release and repository role. This allows the same device, such as a Xiaomi
codename, to have separate HyperOS, MIUI, LineageOS, Evolution X and other source records without merging their
files into an ambiguous profile.

## Local collection

The normal update path is local and Git-based. `tools/hico_collector.py` uses the public Git remotes recorded in
`sources/repositories.json`; normal synchronization does not require GitHub/GitLab API tokens. A shallow,
blobless local cache is kept outside the repository and only the thermal-relevant files and manifests are committed.

## Generation and verification

`tools/hico_generator.py` runs the host `hicod thermal tune` command against each collected thermal file and
then runs `hicod thermal check` against the original file. The source dataset is never modified. Encrypted
Xiaomi `mi_thermald` inputs stay encrypted in the deployable candidate while a readable review copy is stored
when the engine can produce one.

Unknown encrypted formats are recorded rather than guessed. The generated database therefore separates source
facts from HiCo candidate changes and from runtime behavior.
